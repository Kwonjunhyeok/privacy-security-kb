# 신규 자료 감시와 처리 (일 1회 감시 + 주 1회 현행화)

공공기관이 정보보호·개인정보보호 안내서를 새로 내면 하루 안에 지식베이스에 반영하고, 주 1회 전수 점검으로 놓친 것을 잡는다.

| 구분 | 주기 | 하는 일 | 비용 |
|---|---|---|---|
| 감시 `kb-watch` (GitHub Actions) | 매일 06:17 KST | 게시판 목록을 받아 이미 본 게시물과 비교. 새 게시물이 있으면 이슈(라벨 `kb-new-item`)를 연다. AI 미사용 | 없음 |
| 신규 자료 처리 (클라우드 루틴) | 이슈가 열릴 때 | 이슈에 적힌 항목만 수집·검증·반영해 PR 로 올린다. 처리 후 이슈를 닫는다 | 새 자료가 나온 날만 |
| 주간 갱신 (클라우드 루틴) | 주 1회 | `UPDATE.md` 전수 점검(법령·처분·위협·가이드) | 주 1회 |

## 감시 대상
`scripts/watch/boards.json`. 개인정보위 안내서, 개인정보 포털 지침자료, 보호나라 보고서/가이드, 과기정통부 보도자료(가이드 검색)·정책정보.

**KISA 지식플랫폼(가이드라인 2060207, 안내서 2060307)은 감시하지 않는다.** 2026-11-22 시험에서 GitHub Actions 에서는 열렸지만(HTTP 200) 게시물 목록이 HTML 에 없고 나중에 불러와져(목록 링크 1~2건) 스크립트가 새 글을 볼 수 없었다. KISA 자료는 주간 전수 점검(브라우저)이 맡고, KISA 가 재게시하는 개인정보위 안내서는 개인정보위 게시판 감시가 잡는다. KISA 를 일 단위로 보려면 목록을 불러오는 내부 주소를 찾아 `boards.json` 에 넣어야 한다(확인필요). 게시판을 추가하려면 이 파일에 한 줄 더한다(`keywords` 를 주면 제목에 그 낱말이 든 것만 센다).

## 동작 방식
- 상태(이미 본 게시물)는 `watch-state` 브랜치에 저장한다. main 에는 쌓이지 않는다. 처음 보는 게시판은 기준선만 저장하고 이슈를 열지 않는다.
- 새 링크가 한 번에 25건을 넘으면 목록 구조가 바뀐 것으로 보고 이슈 대신 `kb-watch-error` 이슈를 연다.
- 게시판을 읽지 못하면(접속 차단·구조 변경) `kb-watch-error` 이슈를 열고, 모든 게시판이 실패하면 워크플로가 실패해 GitHub 가 알린다.
- 감시는 목록의 제목·번호만 본다. 값의 진위는 루틴의 수집·검증이 맡는다. 감시가 놓쳐도 주간 전수 점검이 잡는다.

## 설정 (한 번만)
1. 이 PR 을 병합한다. 병합 후 Actions 탭에서 `kb-watch` 를 **Run workflow** 로 한 번 실행해 기준선을 만든다(이슈는 열리지 않는다).
2. GitHub 알림: 저장소를 Watch(이슈 포함)로 두면 이슈가 열릴 때 메일·앱 알림이 온다.
3. 클라우드 루틴 새로 만들기 「신규 자료 반영(클라우드)」
   - 환경 `privacy-security-kb`, 모델 Sonnet, 저장소 같은 저장소
   - 트리거: 편집 창의 `+` 로 **GitHub 이벤트**를 추가하고 이벤트 `이슈: 열림`. 필터에 라벨 조건이 없으면 제목 조건(제목에 `새 게시물 감지` 포함)이 있는지 보고, 없으면 필터 없이 두되 지침 1번이 다른 이슈에서 즉시 끝낸다(세션은 시작되지만 아무것도 읽지 않는다). GitHub 이벤트 트리거가 목록에 없으면 이 방식은 쓸 수 없다. 그때는 이슈 알림을 받아 `/kb-cloud-update 신규 자료` 를 직접 실행한다.
   - 지침: 아래 「신규 자료 루틴 지침」
4. 주간 갱신 루틴은 그대로 둔다.

## 신규 자료 루틴 지침
```
너는 정보보호·개인정보보호 지식베이스(이 저장소)의 신규 자료 반영 담당이다. 무인 실행이다. 질문하지 말고 끝까지 진행한다. 오늘 날짜는 `TZ=Asia/Seoul date +%F` 로 구해 TODAY 라 한다.

1. 먼저 트리거가 된 이슈를 읽어 라벨과 제목을 본다. 라벨이 kb-new-item 이 아니거나 제목이 "새 게시물 감지"로 시작하지 않으면 아무것도 읽지 말고 즉시 끝낸다(감시 오류 이슈 등 다른 이슈에서는 실행하지 않는다). 이슈를 읽을 수 없으면 PushNotification 으로 알리고 멈춘다.
2. 이슈 본문의 항목 목록만 처리한다(전수 점검 금지). 그다음 CLAUDE.md, sources.md, UPDATE.md 를 읽고 모델·컨텍스트 분리·수집량 제한 규칙을 따른다.
3. `curl -sS -m 15 -o /dev/null -w '%{http_code}' https://www.law.go.kr` 로 접속을 확인한다. 000 이거나 403 이면 처리하지 말고 이슈에 "접속 차단"을 댓글로 남기고 PushNotification 으로 알린 뒤 멈춘다(attempts 는 건드리지 않는다).
4. 항목마다 kb-guide-curator(가이드·안내서) 서브에이전트로 원문 요약 초안을 kb/_pending 에 쓴다. 이미 kb 에 같은 자료의 이전 판이 있으면 새 판으로 교체 후보(revision)로 쓴다.
5. 별도 kb-fact-checker 서브에이전트(Opus)가 원문과 대조해 판정한다. 통과·수정 후 통과만 kb 로 옮기고 catalog.md, index.md, CHANGELOG.md, 필요 시 crossref.md 를 갱신한다. 보류·기각은 _pending 에 둔다.
6. kb/reports/TODAY.md 에 '## 신규 자료 처리' 절을 덧붙인다(항목, 판정, 이월).
7. 작업 브랜치에 커밋·push 하고 초안 PR 을 만든다(main 직접 push 금지). kb/ 안의 변경뿐이면 kb-check 가 검사 후 자동 병합한다.
8. 이슈에 결과 표(항목 | 판정)를 댓글로 남기고, 모두 처리됐으면 이슈를 닫는다. 보류가 남으면 열어 둔다. 사람이 봐야 할 일(접속 차단, 검사 실패, 보류 3회 도달)이 있을 때만 PushNotification 으로 알린다.
```
